# Совместимость mole с несколькими версиями 3X-UI

Статус: проект решения для реализации; исследование 02.11.2026. Основание — обсуждение в чате и issue [#128](https://github.com/ekho/3xui-mole/issues/128). Пользователь явно исключил поддержку 3.7.0. Продуктовый код и окружения при подготовке документа не менялись.

## Цель и границы поддержки

Один экземпляр mole обслуживает панели разных поддерживаемых версий. Первоначальный список: **3.10.2 и 3.11.0**, основной проверочный образ — 3.11.0. Это конкретные релизы; обещания совместимости со всеми `3.10.x`, `3.11.x`, будущими patch-релизами или форками нет.

3.7.0 исключается из списка поддержки, образов обычных стендов и положительных CI-проверок. 3.10.0 остаётся только источником репетиции обновления существующей установки. Предлагаемая дальнейшая политика — проверенные релизы двух последних стабильных minor-веток; изменение списка происходит отдельным PR с доказательствами, без автоматического допуска по номеру версии.

Версии Xray записываются отдельно. Для исходных проверок используются штатные пары 3.10.2 / 26.10.10 и 3.11.0 / 26.10.21. Другой Xray не превращает известный API панели в неизвестный автоматически, но совместимость его форматов и реального VPN-трафика нельзя считать доказанной этим списком.

### Проверенные upstream-контракты

- В обоих релизах `GET /panel/api/server/status` содержит `obj.panelVersion`, `obj.panelGuid`, `obj.xray.version`. Значения заполняются работающей панелью; для определения версии не нужен зависящий от GitHub `getPanelUpdateInfo`: [3.10.2](https://github.com/MHSanaei/3x-ui/blob/v3.10.2/internal/web/service/server.go), [3.11.0](https://github.com/MHSanaei/3x-ui/blob/v3.11.0/internal/web/service/server.go).
- Клиентские маршруты остаются общими. В 3.11.0 появились `clientHostRuleIds` с различием omitted/empty и диапазонный `keepAlive`: [модель](https://github.com/MHSanaei/3x-ui/blob/v3.11.0/internal/database/model/model.go). `ClientRecord.reverse` имеет собственную JSON-сериализацию в обоих релизах; изменение внутреннего DB-типа не означает необходимость менять наш payload.
- В 3.11.0 `/server/status` доступен ограниченным токенам, однако остальные нужные mole маршруты имеют другие ограничения. Успех status не доказывает наличие прав на client CRUD/settings. Исходный поддерживаемый режим — admin Bearer либо обычная session-авторизация; права не расширяются автоматически: [API scope allowlists](https://github.com/MHSanaei/3x-ui/blob/v3.11.0/internal/web/controller/api.go).
- CLI умеет задавать первого пользователя; в 3.11.0 новая БД получает случайные credentials: [CLI](https://github.com/MHSanaei/3x-ui/blob/v3.11.0/main.go), [создание пользователя](https://github.com/MHSanaei/3x-ui/blob/v3.11.0/internal/database/db.go).

## Выбранный подход

1. Сохранить один `PanelClient` и существующие domain targets. Внутри адаптера — проверка известного релиза и только необходимые преобразования форматов.
2. Добавить один встроенный JSON-реестр поддерживаемых релизов, официальных image digests и проверенных Xray-пар. Go читает его через `go:embed`, Python helpers/CI используют тот же файл. Список upgrade sources хранится отдельно от supported.
3. Для каждой панели сохранять последние версии, `supported|unsupported|unknown` и безопасный reason code. `online` остаётся отдельным признаком. Новые строки и существующие строки после миграции имеют `unknown` до первой успешной проверки.
4. Пул допускает только online, non-retired, supported панели, версия которых всё ещё присутствует в текущем реестре. Операции над уже назначенным клиентом не меняют назначение автоматически.
5. Проверка при выборе сервера — лишь ранний фильтр. Перед заказом/исполнением и непосредственно перед изменяющим HTTP-запросом нужен актуальный допуск. Между проверкой и отправкой нет атомарной гарантии upstream; обновление панели во время операций исключается runbook и обнаруживается по ошибкам/readback.

Полные отдельные реализации клиентов по версиям сейчас дают дублирование без подтверждённой пользы. Автоматическое «угадывание возможностей» изменяющими запросами небезопасно. Общий универсальный framework capabilities/плагинов не нужен: дополнительные признаки вводятся вместе с реальной функцией mole, которая ими пользуется.

## Поведение при отказе

- Неизвестная/неподдерживаемая версия: диагностическое чтение разрешено в рамках известных read endpoints; новые клиентские записи запрещены. HTTP 401/403/404, TLS error, malformed response и timeout не означают отсутствие клиента или отсутствие функции.
- Временная невозможность подтвердить версию до lease: короткий `JobSnooze(1 minute)`, без увеличения domain attempts и без write/reset markers. Наблюдение сервера показывает unknown и причину.
- Подтверждённая неподдерживаемая версия у уже подготовленной операции: существующий переход в `needs_review`, с причиной `panel_version_unsupported` и неизменными target/финансовыми фактами; markers не поднимаются только ради такого перехода. Для trial, где отдельного review_reason нет, причина видна в server compatibility; новую trial-схему ради неё не добавлять.
- Если запись могла произойти раньше, сохраняются markers и действующие ограничения повторов. Изменение версии во время исполнения требует review; считать такую операцию гарантированно не записавшей нельзя.
- Глобальное разрешение повторного неопределённого create удаляется. Отсутствующее/false legacy env допускается как устаревшее значение, true отклоняется при загрузке конфигурации с понятной причиной. При действительно отсутствующем клиенте восстановление требует расследования: оператор восстанавливает точный frozen target контролируемо, затем существующий reconcile подтверждает его чтением. Автоматического второго create не происходит.
- Receipts/webhooks продолжают сохраняться и проверяться. Оплаченный заказ не становится refunded/failed автоматически из-за несовместимости; возвращение к исполнению — существующим recovery-процессом с прежним target.
- Ручной VPN-ban и повторный reset остаются особо защищёнными. Отказ молча потерять возможность повторно применить ban после reset должен приводить к review и понятной причине, а не к заявлению об успешной блокировке.

## Приёмка и границы работ

Обязательны одинаковые core-сценарии на обеих версиях, отдельный смешанный пул, проверки неизвестной версии/прав/timeout и обновление с восстановлением исходной БД. Принятие поддержки — после runtime evidence; fixtures и успешный CI без реальной панели этого не заменяют.

Новые экраны host rules, новые протоколы, kernel AmneziaWG, установка/обновление production и изменения финансовых правил не входят. Совместимость произвольного Xray, альтернативных форков и master/node не обещается без отдельного прогона соответствующей topology.

Существующая 3.10.0 после включения новой политики не допускается к мутациям. Перед rollout требуется выяснить версии реальных панелей, обновить их до поддерживаемого релиза и выполнить проверку. Без этого включать policy в production нельзя.

Восстановление 3.10.0 в rehearsal проверяет сохранность данных панели. Продолжение новых записей старой production-версией после такого отката потребовало бы и возврата соответствующего предыдущего release mole; новый executable не должен обходить собственный список поддержки ради rollback.
